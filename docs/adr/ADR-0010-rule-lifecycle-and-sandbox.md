# ADR-0010: 規則の段・寿命・上限と、サンドボックスの段階

- 状態: 提案（2026-11-04。人の判断13件を反映済み。マージをもって採用）
- 日付: 2026-11-04
- 依存: ADR-0001、ADR-0004、ADR-0005、ADR-0009
- 範囲: この ADR は文書だけ（U0）。コード・CI・baseline・個人情報ゲート（repo-preflight）は変えない。

## 背景

ラチェットは、一度できた検査を後戻りさせない仕組みである。一方で、規則を足し続けるだけだと、
見直されない規則が積み上がり、身動きの取れない部屋になる。いまの main には次の弱さがある。

- 規則は 6 adapter・11 本（下の表）あるが、段（どれだけ強く止めるか）・作成日・見直し日・
  発火数を持たない。引退や降格の手順も無い。
- 期限付き waiver（`ai-ratchet-gate.waivers/v1`）には期限の上限が無い。
- 試作の段階でも本流と同じ強さで止まるため、試すために baseline を広げる逃げ道に寄りやすい。

方針は 2026-11-04 に人が決めた（規則を3段に分ける・寿命と上限・サンドボックスの段階・本流へ戻す関門・
足すなら1つ引退）。この ADR はそれを、このリポジトリの言葉と順番に落とす。

## 決定

### 1. 規則を3段に分ける

| 段 | 意味 | 止め方 | 見直し |
|---|---|---|---|
| absolute（絶対ゲート） | 個人情報・秘密・認可・権限の拡大 | 1件でも deny。waiver・サンドボックス例外・引退・降格の対象にしない | 見直しの対象外。変更は人の承認 |
| ratchet（ラチェット規則） | 既存は許し、新しい悪化だけ止める | 今の挙動（baseline 外の新規だけ deny） | 90 日ごと |
| advisory（助言） | スタイル・命名など | deny しない。件数だけ残す。既定はオフ | 30 日で降格候補 |

- 段はコード（各 adapter の規則定義）に置く。JSON やサンドボックスのファイルでは段を変えられない。
- いま advisory に当たる規則は無い。枠だけ作る。

いまの 11 本の段:

| adapter_id | rule_id | 段 |
|---|---|---|
| `git.tracked_ignored` | `tracked_ignored` | ratchet |
| `skills.provenance` | `new_skill` | ratchet |
| `skills.provenance` | `allowed_tools_token` | absolute |
| `skills.provenance` | `unrestricted_tools` | absolute |
| `skills.provenance` | `executable_asset` | absolute |
| `test.disable` | `unconditional_skip` | ratchet |
| `test.disable` | `focused_only` | ratchet（判定は今の `strict` のまま。1件でも deny） |
| `test.disable` | `hollow_test` | ratchet |
| `ci.pin_tagged` | `pin_not_tagged` | ratchet |
| `ci.release_asset_live` | `release_asset_not_live` | ratchet |
| `ci.secret_declared` | `secret_not_registered` | ratchet |

skills の権限系3本は「道具や実行できるものが広がる」失敗を止めるため、absolute に置く。
いまの baseline はどれも 0 件なので、段を入れても今の判定は変わらない。

### 2. 寿命と上限

- 各規則に、作成日・防ぐ失敗（コードの定義）と、直近 90 日の発火数・誤検知数・状態・残す根拠
  （リポ内の運用状態ファイル）を持たせる。状態は「有効・見直し候補・降格・引退」の4つ。それ以外は fail-closed。
- 既存の規則の作成日は、その規則を入れたコミットの日付とする。
- 90 日発火の無い ratchet 規則は「見直し候補」に載せる。発火しないのは守れている証拠のこともあるので、
  候補に載せるだけで、引退は人のレビューで決める。残すときは「残す根拠」を書く（残す根拠を示す方式）。
- 見直し期限を過ぎても CI は赤にしない。定期チェックで知らせるだけにする（関係のない PR を止めないため）。
- 有効な ratchet 規則は約 20 本までとし、超えたら検査を赤にする。上限・期間の数はコードの定数に置き、
  JSON では変えない。
- 発火数は receipt の横に置く別ファイルに、規則ごとの件数だけを書いて数える。
  receipt（`ai-ratchet-gate.receipt/v1`）は動かさない。subject_key と message は出さない。
- 誤検知数は、誤検知を直す PR に1行残し、それを数える（OPERATIONS の「誤検知時の扱い」に手順を足す）。

### 3. 規則を足す条件と、足すなら1つ引退

- 規則を足すのは、**同じ失敗が2回起きたとき**とする。1回の失敗では規則を増やさない。
  足す提案には、2回の失敗それぞれの出どころ（PR・CI の記録など、公開してよい参照）を添える。
- 規則を足す提案には、引退させる既存の規則の候補を1つ必ず添える。この検査は比較元の版で動く
  base-guard の側に置き、機械的に止める（配線は U9 で人の判断を経て行う）。
- absolute 段の追加・変更は、どれも人の承認が要る。

### 4. 例外は期限付き（最大 14 日）

- 例外（waiver とサンドボックスの例外）は最大 14 日とし、期限が切れたら適用しない（本流の規則に戻る）。
- 本流の waiver にも同じ上限をかける。新しい waiver は v2（発行日時と rule_key を持つ）で書き、
  v1 は読み続ける。
- absolute 段の規則と repo-preflight の検査は、例外の対象にできない。書いたら fail-closed で止める。

### 5. サンドボックスの段階

| 段階 | 効く規則 |
|---|---|
| innovation | 絶対ゲートだけ |
| feature | 絶対ゲートと、関連する ratchet 規則 |
| strict | 本流と同じ |

- サンドボックスは同じリポの `sandbox/*` の枝とする（repo-preflight をそのまま使える）。
- どの段階を使うかは判定する側（CI）が決め、PR の中身では決めない。main に向けた PR は、
  サンドボックスの設定を無視して必ず strict で判定する。
- サンドボックスの枝でも、push のたびに repo-preflight を回す（個人情報は早く止める）。

### 6. 本流へ戻す関門

main に戻すときは、次の4つをすべて満たす。判定と報告までを道具が行い、マージは人が行う。

1. 絶対ゲート（repo-preflight と absolute 段の規則）を例外なく全部通す。
2. 緩めた規則ごとに「失敗が起きていない証拠」「規則の更新案」「期限付き例外の承認」のどれかを示す。
3. 本流の規則一式で影の実行をし、サンドボックスの段階での判定との差分を添える。
4. 緩めた規則・得た価値・残るリスク・規則への影響を短くまとめる。

### 7. 個人情報ゲート（repo-preflight）は対象外で、弱めない

- 個人情報ゲート（実ホームパス・個人メール・個人名義・鍵の形・secret の検査）は絶対ゲートであり、
  どの段階・どの例外でも外さない。上限・見直し・引退・降格の数にも入れない。
- ai-ratchet-gate は repo-preflight の検査を作り直さず、名前を絶対ゲートとして並べるだけにする。
  呼び出し・SHA 固定・baseline は、この ADR と後続のどの単位でも変えない。

### 8. 人の停止線に足すもの

OPERATIONS の「自動化してよい範囲 / 人間停止線」に、次を足す（後続の単位で文書を直す）。

- 規則の段の変更（特に absolute に関わるもの）
- 上限・期間の定数の変更
- サンドボックスの段階の追加
- CI への配線と必須化（まず影で約 2 週間回し、差分を人が読んでから決める）

### 9. 担い手

- 実装と PR は係（エージェント）が1単位ずつ出してよい。マージは人が行う。
- マージを自動化する仕組みと条件は、別の案として人の判断を経る。どの場合も個人情報ゲートは弱めない。
- 形式検証（TLA+・Lean）は当面ローカルで回し、CI の必須にはしない。安定したら影で回す。

## 後続の単位（順番だけ。どれも別の PR）

1. U1 規則の定義（段・防ぐ失敗・作成日をコードに置く）
2. U2 規則の運用状態ファイルの読み込みと検査
3. U3 段で判定する
4. U4 発火数の材料と見直し候補の一覧
5. U5 例外 v2（14 日の上限）
6. U6 足すなら1つ引退の差分検査
7. U7 サンドボックスの段階
8. U8 本流へ戻す関門
9. U9 CI への配線（人の判断。まず影で回す）
10. U10 初回の見直し

どの単位も、振る舞いのテストを先に書き、既存のテストと `scripts/verify.py` が緑のままであることを
完了条件にする。

## 結果

- 段と上限があるので、規則の数と強さを、決めた枠の中で保てる。
- 発火の無い規則が見える形で残り、引退・降格を人がレビューして決められる。
- 試作は段階を下げて速く回せるが、main に入るときは必ず strict と絶対ゲートを通る。
- 規則を足す手間が増える（2回の証拠と引退候補が要る）。これは意図した重さである。
- CI そのものも見直しの対象にする。検査を足しすぎず、リポごとに必要十分であることを保つ。

## 未決（U5 の前に人が決める）

- 本流の waiver v1 は、観測（つまり HEAD の SHA）に束縛されるため、事実上1コミットにしか効かない。
  14 日の例外を実際に使うには束縛を緩める必要があるが、それは束縛を弱めることになる。
  緩めるかどうか、緩めるなら何への束縛を残すか（rule_key・finding_id・期限は残す案）を、U5 の前に人が決める。
  それまでは本流の waiver の束縛を変えない。

## 検討した代替案

- **規則の定義を JSON に置く**: PR がその JSON を書き換えて段を下げられるため採らない。
- **見直し期限切れを CI の赤にする**: 関係のない PR まで止まるため採らない。
- **失敗が1回起きたら規則を足す**: 規則が増え続けるため採らない（2回で足す）。
- **サンドボックスを使い捨てのリポにする**: repo-preflight の配線を毎回作ることになるため採らない。
